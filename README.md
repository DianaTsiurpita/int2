# Laboratory Work 2 — Secret Management and User Authentication

Based on Practice 1: FastAPI Orders API, internal Forecast API, PostgreSQL.

## Start on Windows PowerShell

Use a **separate** project name to avoid collisions with other laboratories.

```powershell
Copy-Item .env.example .env
.\setup-secrets.ps1
docker compose -p integration-lab2 up -d --build
docker compose -p integration-lab2 ps
```

**Note:** the source archive for Practice 1 omitted `forecast-service/data/ames_train.csv`. This distribution restores the Ames training CSV from the previously supplied laboratory project. The model is trained at image build time as in Practice 1.

## API

Host: http://localhost:8000; Forecast API port 8001 is not published. Swagger: http://localhost:8000/docs.

Public: `GET /health`, `POST /auth/register` (JSON username/password, 201), `POST /auth/login` (form-encoded username/password, 200).

Authenticated (Bearer JWT): `GET /auth/me`, `GET /orders`, `GET /orders/{id}`, `POST /orders`, `PATCH /orders/{id}`, `DELETE /orders/{id}`. The orders CRUD schema and graceful degradation remain from Practice 1.

Passwords are Argon2id-hashed; tokens use HS256, `sub`, `iat`, `exp`; lifetime is configured with `ACCESS_TOKEN_EXPIRE_MINUTES` (default 30).

## Secrets and access policy

`secrets/db_password` is mounted into postgres and orders-api, `secrets/jwt_secret_key` into orders-api only. Neither is passed in environment variables or baked into images. They are generated by `setup-secrets.ps1`; do not commit them. `.env` contains only non-sensitive settings.

On Linux use `chmod 600 secrets/db_password secrets/jwt_secret_key`. On Windows the setup script applies restrictive ACLs.

## Tests and experiments

The repository includes `uv.lock`; Dockerfiles install dependencies using this lockfile. Do not commit real secret files.
See `TESTS_UA.md` for T1–T12 and experiments R3.2–R3.5. Record **actual** outputs in `REPORT.md` after running the tests. Do not claim experiments passed before running them.

**PostgreSQL password rotation:** changing the mounted file does not change an already initialized PostgreSQL role password. Development: back up data, update password with `ALTER ROLE`, change secret, recreate clients; resetting the volume is acceptable only for disposable data. Production: back up, coordinate transactional password change and secret distribution, recreate clients with minimal downtime, verify connections, preserve the volume.
