# Лабораторна робота №2 — результати

**Тема:** Управління секретами та автентифікація користувачів в інтегрованій мікросервісній системі.

**Статус:** Основні функціональні сценарії та експерименти R3.2–R3.5 виконано. Тести T1–T12 перевірено; T3 проводився в ізольованому Compose-проєкті.

## Експерименти R3.2–R3.5

### R3.2 — Ротація JWT-ключа

Після заміни секретного ключа підписування JWT і перезапуску Orders API раніше виданий токен був відхилений із HTTP 401. Повторна авторизація дозволила отримати новий токен.

**Результат:** підтверджено недійсність старих JWT після ротації ключа. **Доказ:** скриншот 9.

### R3.3 — Відсутність секрету

Файл `jwt_secret_key` тимчасово вилучили та повторно створили контейнер Orders API. У журналі зафіксовано повідомлення `RuntimeError: Required secret jwt_secret_key is unavailable at /run/secrets/jwt_secret_key`. Після відновлення файлу сервіс запустився.

**Результат:** підтверджено механізм fail-fast для обов'язкового JWT-секрету. **Доказ:** скриншот 12.

### R3.4 — Перевірка ротації пароля PostgreSQL

Перед експериментом створено та перевірено резервну копію бази PostgreSQL у форматі custom dump. Збережено копію початкового файлу `db_password`.

Згенеровано новий випадковий пароль і записано його у файл `secrets/db_password`. Після цього сервіси `postgres` та `orders-api` пересоздано командою `docker compose up -d --no-deps --force-recreate postgres orders-api`.

PostgreSQL перейшов у стан Healthy, а Orders API запустився. Однак підключення Orders API до PostgreSQL з новим паролем завершилося помилкою `FATAL: password authentication failed for user "orders"`.

Початковий секрет відновлено, контейнери повторно пересоздано. Контрольне підключення повернуло `DB CONNECTION: SUCCESS`, кількість користувачів залишилася незмінною — `USERS: 2`, а `GET /health` повернув `ok`.

**Результат:** експериментально підтверджено, що `POSTGRES_PASSWORD_FILE` застосовується під час першої ініціалізації тому PostgreSQL, а зміна файлу секрету не змінює пароль наявної ролі автоматично. Дані збережено.

**Безпечна ротація в development:** створити резервну копію; змінити пароль ролі PostgreSQL через `ALTER ROLE`; синхронізувати файл секрету; пересоздати залежні сервіси; перевірити підключення та дані. Видалення тому не потрібне.

**Безпечна ротація в production:** створити й перевірити резервну копію; підготувати план відкату; погодити вікно змін; узгоджено змінити пароль ролі та секрет; оновити підключення клієнтів; перевірити доступність і збереження даних. Том PostgreSQL не видаляти.
### R3.5 — Недоступність Forecast API

Forecast API було зупинено. Створене через Orders API замовлення мало `predicted_price = null`; після тесту Forecast API запущено знову.

**Результат:** підтверджено graceful degradation: авторизований POST /orders повернув HTTP 201 та predicted_price = null. **Доказ:** скриншот 10.

## Підсумковий висновок

У лабораторній роботі реалізовано інтегровану мікросервісну систему з PostgreSQL, Orders API та внутрішнім Forecast API. Секрети передаються через Docker Compose Secrets, реалізовано реєстрацію користувачів, Argon2id, JWT HS256 і захист операцій із замовленнями.

Перевірено сценарії T1–T12, зокрема відмову за відсутності секрету в ізольованому Compose-проєкті, ротацію JWT, недоступність Forecast API та зміну секрету PostgreSQL із перезапуском сервісів.

Експеримент R3.4 підтвердив, що зміна `POSTGRES_PASSWORD_FILE` не оновлює пароль ролі в уже ініціалізованій базі. Після відновлення початкового секрету працездатність системи та збереження двох користувачів підтверджено.
## Контрольні питання

**1. Канали витоку секретів зі змінних середовища.** Значення можуть потрапити до `docker inspect`, `docker compose config`, `/proc/<pid>/environ`, журналів CI/CD, історії команд оболонки та діагностичних дампів процесів.

**2. Конфігурація та секрети.** `MODEL_VERSION`, `FORECAST_TIMEOUT`, `POSTGRES_USER`, `ACCESS_TOKEN_EXPIRE_MINUTES` — звичайні параметри конфігурації: їх розкриття саме по собі не надає доступу. `db_password` і `jwt_secret_key` — секрети: перший відкриває доступ до БД, другий дозволяє підписувати JWT.

**3. Compose і Swarm secrets.** У звичайному Docker Compose секрети є файлами на хості, змонтованими в контейнер лише для читання. У Swarm передбачені кероване розповсюдження секретів, шифрування в Raft-журналі та захищена передача між вузлами. Compose не є повноцінним сховищем секретів.

**4. Ротація пароля PostgreSQL.** `POSTGRES_PASSWORD_FILE` використовується офіційним образом під час початкової ініціалізації тому. Подальша зміна файлу не виконує `ALTER ROLE` в уже створеній БД. Для розробки: зробити резервну копію, змінити пароль ролі через SQL, оновити файл секрету, пересоздати клієнтські контейнери та перевірити з’єднання; видаляти том можна лише за відсутності цінних даних. Для production: зробити перевірену резервну копію, спланувати вікно ротації, узгодити зміну пароля в PostgreSQL і доставку нового секрету, перезапустити залежні сервіси, перевірити доступ і зберегти том та план відкату.

**5. Argon2id/bcrypt замість SHA-256.** SHA-256 є швидкою хеш-функцією і полегшує масовий перебір паролів. Argon2id і bcrypt навмисно затратні за ресурсами. Salt — випадкове значення для кожного пароля, яке перешкоджає використанню попередньо обчислених таблиць і збігу хешів однакових паролів. Work factor — параметр обчислювальної складності; Argon2id додатково використовує параметри пам’яті й паралелізму.

**6. Структура JWT.** JWT містить три частини, розділені крапками: Base64URL-кодований header, payload із твердженнями (`sub`, `iat`, `exp`) і криптографічний підпис. Зміна payload без повторного підписування призводить до невідповідності підпису й відхилення токена.

**7. `alg: none` та algorithm confusion.** Атака `alg: none` намагається змусити сервер прийняти непідписаний токен. Algorithm confusion використовує неправильне трактування алгоритму або ключа перевірки. У проєкті `jwt.decode(..., algorithms=['HS256'])` задає дозволений алгоритм явно.

**8. HTTP 401 та `WWW-Authenticate`.** Код 401 означає відсутню або недійсну автентифікацію. Заголовок `WWW-Authenticate: Bearer` повідомляє клієнту про необхідність Bearer-токена. Наприклад, `GET /orders` без JWT повертає 401.

**9. Наслідки ротації JWT-ключа.** Старі JWT підписані попереднім ключем, тому після заміни ключа і перезапуску Orders API їхній підпис більше не перевіряється; запити отримують 401. Потрібна повторна авторизація.

**10. Однакові помилки входу.** Однаковий текст відповіді для невідомого користувача та неправильного пароля ускладнює user enumeration — визначення існування облікових записів за відповідями сервера.

**11. Публічний health та приватний Forecast API.** `GET /health` потрібен для перевірки працездатності без облікових даних. Forecast API не публікує порт на хості: Orders API залишається єдиною зовнішньою точкою входу, централізує автентифікацію та обмежує поверхню атаки.

**12. Stateless JWT та відкликання.** Сервер перевіряє підпис і термін дії токена без зберігання сесії. Тому окремий JWT не можна негайно відкликати без додаткових механізмів: списку блокування, версії токена/користувача, короткого TTL або ротації ключа, яка відкликає всі токени, підписані старим ключем.
